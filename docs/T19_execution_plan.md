## 3. 요청과 사진 특성의 입력 계약

`generator.py`는 비어 있지 않은 요청 문자열과 T18 결과 객체를 받는다. 사진 경로를 모델이 선택하거나 파일 내용을 모델이 직접 읽게 하지 않는다.

| T18 입력 | 사용 목적·보존 규칙 |
|---|---|
| `schema_version=1`, `source.path`, `source.sha256` | 지원 계약 및 대상 사진 식별. 평가 시 실제 고정 RAW의 해시와 대조한다. |
| `exif.iso`, `shutter_seconds`, `camera`, `white_balance` | 촬영 맥락과 WB 근거. 누락된 온도·계수를 임의로 채우지 않는다. |
| `analysis.pipeline_version`, `color_space`, `wb_applied`, 디코더 정보 | 현재 측정 기준 `t18-linear-rgb-v1`·선형 sRGB와 촬영 WB 적용 여부를 확인한다. ART 렌더와 같은 측정이라고 가정하지 않는다. |
| `histogram.luminance.mean`, `shadow_fraction` | 노출 판단 보조. 평균 휘도 하나로 EV 보정량을 정답처럼 역산하지 않는다. |
| `histogram.saturation.mean`, RGB별 `mean/counts/probabilities`, `bin_edges` | 채도·채널 분포 근거. 채널마다 16개 bin이라는 계약을 확인한다. |
| `signals.is_dark`, `yellow_tendency`, `deferred_reasons` | `true/false/null`을 구분한다. 경계·누락으로 보류된 `null`을 `false`로 바꾸지 않는다. |
| `warnings` | 판단 제한을 결과에 전달한다. 특히 `wb_applied=unity`일 때 색 경향을 확정하지 않는다. |

객체 입력의 수치 정밀도를 유지하고 입력을 변경하지 않는다. JSON 전달은 T18의 `dumps_features`를 사용한다. 소수 6자리로 반올림된 JSON에서 신호를 다시 판정하지 않는다. 지원하지 않는 특성 버전, 잘못된 타입·비유한 수치·구조 결함은 생성 전 오류로 반환한다.

처리 순서는 **요청+특성 검증 → 필요한 도구와 근거 결정 → 허용 키·제약을 적용한 구조화 제안 → 결정적 검증 → .arp 직렬화 → 재검증**이다. 밝기만 요청하면 WB·채도는 변경하지 않는다. `yellow_tendency`는 장면 색의 영향도 받으므로 색온도의 정답이나 중립색 검출 결과로 취급하지 않는다. “더 밝게”의 기존 세션 기준 증분 계산은 T21로 남기고, 이번에는 중립 기준의 단일 프로필을 만든다.

## 4. .arp 키·제약 후보와 초기 선택

[키 목록](arp_schema.md)은 그룹·키 이름만 정의하며 타입·범위·결합 규칙을 모두 제공하지 않는다. 따라서 이름은 해당 문서에 대조하고, 타입·단위·열거값은 `rtengine/procparams.h/.cc`, 수치 범위는 기존 GUI 및 상수를 읽어 교차 확인한다. 아래 수치는 소스에서 확인한 후보 제약이며, 구현 첫 단계에서 같은 기준 소스로 재확인해 `schema.json`에 고정한다.

| 그룹·키 | 타입·후보 범위 | 초기 선택·결합 제약 및 근거 |
|---|---|---|
| `[Version] Version` | 정수, 현재 `1045`와 정확히 일치 | 모든 결과에 필수. 모델이 만들지 않고 호스트가 기록한다. `procparams.cc`의 저장·로드 경로가 근거다. |
| `[Exposure] Enabled` | boolean | 노출을 선택하면 `true`를 명시한다. |
| `[Exposure] Compensation` | 유한 실수, `-12..12` EV | 밝게·어둡게 요청의 핵심 키. GUI 간격 `0.05`는 범위와 별개이며 강제 양자화하지 않는다. `rtgui/exposure.cc` 근거. |
| `[Exposure] Black` | 유한 실수, `-2..2` | 후보로 기록하되 v1의 모델 변경 허용 키에서는 제외한다. 명시 지원을 추가하기 전에는 검정점 요구를 지원 범위 밖으로 반환한다. |
| `[White Balance] Enabled` | boolean | WB를 선택하면 `true`를 명시한다. |
| `[White Balance] Setting` | 문자열, v1은 `Camera` 또는 `CustomTemp` | `Custom` 같은 추측값을 허용하지 않는다. 실제 저장 열거값은 `procparams.cc` 근거. `Auto`·`CustomMult`·`CustomMultLegacy`는 v1 제외. |
| `[White Balance] Temperature` | 정수, `1500..60000` K | `CustomTemp`에서 필수. `procparams.h`, `rtengine/colortemp.h` 및 `rtgui/whitebalance.cc` 근거. |
| `[White Balance] Green` | 유한 실수, `0.02..10` | `CustomTemp`에서 필수. 위 상수 및 GUI 근거. `Camera` 분기에서는 Temperature·Green을 출력하지 않는다. |
| `[White Balance] Equal` | 유한 실수, v1에서는 출력하지 않음 | 기존 기본값 `1.0`에 맡긴다. 모델 변경 금지. |
| `[White Balance] Multipliers` | 기존 형식은 3개 계수 목록 | v1 제외. T18의 `r/g1/b/g2` 4계수와 직접 대응하지 않으며 그대로 복사하거나 온도로 환산하지 않는다. |
| `[Saturation] Enabled` | boolean | 채도·생동감을 선택하면 `true`를 명시한다. |
| `[Saturation] Saturation` | 정수, `-100..100` | 채도 요청의 핵심 키. `procparams.h`, `rtgui/saturation.cc` 근거. |
| `[Saturation] Vibrance` | 정수, `-100..100` | 생동감 요청에 선택. Saturation과 별도 의도로 다룬다. 같은 소스 근거. |

모델이 변경할 수 있는 v1 키는 노출 보정, WB 방식·온도·Green, 채도·생동감으로 제한한다. `Enabled`와 Version은 호스트가 조립한다. ToneCurve·노이즈·선명도·렌즈·RAW 전처리·파일 경로 관련 키는 이 카드의 초기 허용 목록에 넣지 않는다.

WB는 `Camera` 보존과 `CustomTemp` 수치 지정을 구분한다. **현재 T18의 온도 필드는 `null`로 출력되므로 촬영 WB의 Kelvin 기준이 있다고 가정할 수 없다.** “노란 기를 줄여줘”만으로 특정 온도를 발명하지 않는다. 명시적인 절대 온도/Green 또는 추적 가능한 기준값이 있는 경우만 `CustomTemp` 수치를 제안하고, 기준이 없으면 `needs_input`과 부족 항목을 반환한다. 노출·채도만 있는 요청에는 WB 그룹을 생략해 중립 프로필의 촬영 WB를 유지한다.

범위 밖 값을 조용히 자르거나 타입을 강제로 바꾸지 않는다. 범위는 기존 도구의 입력 한계이며 사진 품질의 보증이 아니다. 보수적인 추천 폭이 필요하면 별도 생성 정책으로 설명하고, 그 폭을 ART 고유 제약으로 표기하지 않는다.

Lightroom과 ART의 `.arp`는 파라미터 의미·스케일·처리 순서가 달라 **정확한 일대일 매핑이 아니다.** 같은 이름이나 숫자로 같은 영상 결과를 보장하지 않는다. T19는 Lightroom 값을 직접 복사하는 변환기를 구현하지 않으며, 후속 사례 기반 추천에서도 이 한계를 유지한다.

## 5. schema.json과 검증 전략

`src/artagent/arp/schema.json`은 선택한 키의 구조화 표현을 검증하는 기계 판독 계약으로 만든다. JSON Schema 방식의 타입·필수값·enum·범위·조건부 필수값·알 수 없는 속성 거부를 사용한다. 실제 검증 라이브러리는 구현 시 venv 설치를 확인한 뒤 해당 계약을 검증할 수 있는 기존 경로를 우선 사용한다.

구조화 프로필은 `ppversion`과 `groups`를 갖는다. `groups`에는 선택한 실제 `.arp` 그룹·키만 넣는다. 모델 제안의 변경 키는 §4의 허용 목록으로 제한하고, 호스트 조립 뒤 Version·Enabled를 포함한 최종 객체 전체를 검증한다. 요청·특성 해시, 선택 이유, 경고, 런타임 정보는 결과 봉투에 두고 `.arp` 키로 직렬화하지 않는다. 이를 위해 새 `.arp` 형식을 만들지 않는다.

1. **문서 대조:** 선택한 모든 조정 키가 `docs/arp_schema.md`의 정확한 그룹·대소문자·띄어쓰기에 존재하는지 검사한다. `[Version]`은 해당 목록에 빠져 있으므로 기존 `procparams.cc` 저장·로드 근거로 별도 메타데이터 예외를 명시한다. 임의의 도구 키를 같은 예외로 허용하지 않는다.
2. **구조·타입:** 알 수 없는 그룹·키, 중복 JSON 키, 중복 INI 그룹·키, 빈 제안, 숫자 문자열, boolean을 숫자로 쓰는 입력, 정수 필드의 비정수, `NaN/Infinity`를 거부한다. JSON Schema 외에 필요한 엄격한 파싱 검사를 수행한다.
3. **수치·결합:** 표의 포함 경계, WB 분기별 필수값, 선택 도구의 `Enabled=true`, 요청에 선택하지 않은 도구 변경 금지를 검사한다. Saturation 그룹에는 Saturation/Vibrance 중 선택한 조정이 하나 이상 있어야 한다. WB 수치 근거 누락은 정상 프로필로 세지 않는다.
4. **버전:** 시작 시 `rtgui/ppversion.h`의 `#define PPVERSION`을 읽어 스키마의 지원 버전과 비교한다. 생성 객체의 `ppversion`, 직렬화한 `[Version] Version`도 같은 값이어야 한다. 파일을 찾지 못하거나 유일한 정수 정의를 얻지 못하면 실패한다.
5. **직렬화 후 검증:** 그룹·키 순서, UTF-8·개행, 소수점 `.` 및 boolean `true/false`를 고정한다. INI 파서는 대소문자를 보존하고 보간을 끈다. 다시 읽어 구조화 값·타입·허용 키·버전이 보존되는지 대조한다. 임의 문자열을 INI 본문에 삽입하지 않는다.
6. **최종 형식 확인:** 통과한 프로필을 실제 ART-cli에 전달한다. CLI가 알 수 없는 키를 무시하거나 기본값으로 처리할 수 있으므로 렌더 성공만으로 키·제약 검사를 대신하지 않는다.

`schema.json`의 JSON 구조 버전, T18의 특성 버전, `.arp`의 PPVERSION은 서로 다른 계약이다. 한 버전의 증가로 다른 버전 불일치를 덮지 않는다.

## 6. generator.py와 런타임 설계

후속 구현 파일은 카드대로 `src/artagent/arp/schema.json`, `__init__.py`, `generator.py`, `tests/test_arp_generator.py`를 중심으로 한다. 새 프레임워크·패키징 구조를 만들지 않는다.

`generator.py`는 다음 책임을 순서대로 수행한다.

1. 스키마·헤더의 PPVERSION, 요청·T18 입력을 확인한다. 비용이 드는 호출보다 앞서 실패시킨다.
2. 요청과 사진 특성에서 필요한 도구·근거·누락 정보를 정리한다. 지원 범위 밖 요청은 `unsupported_request`, 필요한 WB 기준 부재는 `needs_input`으로 반환한다.
3. 필요한 특성·허용 키·제약만 담아 런타임에 구조화 JSON 제안을 요청한다. 파일 편집·셸 실행·임의 키 추가는 모델의 역할에 넣지 않는다. 호스트에서 허용 키·근거·버전을 다시 검증한다.
4. 호스트가 Version·Enabled를 조립하고 결정적 검증을 수행한다. 실패 시 `validation_error`와 실패 키·제약을 반환하고 `.arp`를 쓰지 않는다. 요청 실패·시간 초과·잘못된 JSON은 `runtime_error`로 구분한다.
5. 통과 결과만 결정적 `.arp` 텍스트로 만든다. 호출자가 정한 출력 경로에만 기록하며 RAW와 기존 sidecar를 보존한다. 결과는 구조화 프로필·`.arp` 텍스트·선택 이유·경고·런타임 기록을 함께 반환한다. `needs_input` 등에서는 프로필을 반환하지 않는다.

입력 객체와 런타임 호출 함수를 주입할 수 있게 해 오프라인 pytest와 실제 생성 평가가 같은 검증·직렬화 경로를 타도록 한다. 최소 공개 계약은 “요청·특성·주입 런타임 → 상태와 생성 결과”이며, 구체 함수명은 구현 시 정한다. 독립 실행 검증용 `python -m artagent.arp.generator`에는 argparse와 `main()` 가드를 두고 `--request`, `--features`, `--output`을 받도록 한다. 이 절의 명령 인터페이스는 아직 구현되지 않았다.

### 런타임 인수

조사 기준의 `src/artagent/answer.py::generate_llm_response`는 `LLM_PROVIDER`를 사용하며 기본 분기는 `codex`, 모델 선택은 `LLM_MODEL → CODEX_MODEL → 코드 기본값 gpt-5.6-sol` 순서다. 별도의 명시적 호환 API 분기도 있다. 이는 **현재 소스의 기본값**이며, 지금 실행 중인 실제 제공처·모델을 확인한 결과는 아니다.

구현 착수 시 실제 사용 중인 제공처·모델·실행 파일 버전·기존 실행 정책·timeout·구조화 응답 지원을 확인해 이 절과 실행 기록에 남긴다. 현 설정을 승계하고 새 모델을 미리 선정하지 않는다. 키·토큰 값은 기록하지 않는다. 제공처 실패 시 다른 제공처로 자동 전환하지 않는다.

기존 함수는 `answer/citation_ids` 등 답변 전용 JSON 검증을 내장하므로 그대로 호출해 프로필 JSON을 받을 수 있다고 가정하지 않는다. `generator.py` 안의 작은 T19 전용 어댑터에서 현재 제공처의 호출 방식·도구 비활성화 정책을 따르고, 응답에는 §4~5의 프로필 계약을 적용한다. 기존 답변 모듈의 계약을 바꾸지 않는다. 재사용 가능한 실행 정책·메타데이터 처리 단위는 구현 시 확인하며, 호환되지 않으면 연결 작업을 먼저 끝낸 뒤 실제 20건 평가로 진행한다.

T19 평가에서는 입력당 생성 호출 **1회**를 원칙으로 한다. 실패 시 같은 입력의 재호출로 최초 실패를 지우지 않는다. 렌더 오류 피드백으로 재생성하는 ≤3회 루프는 T20에서 구현한다. 런타임 없이 규칙만으로 만든 출력이나 모의 응답 결과를 실제 생성 평가로 보고하지 않는다.

## 7. pytest와 20개 생성 평가

`tests/test_arp_generator.py`에 오프라인 계약 검사와 실제 실행 검증의 경계를 명확히 둔다. 아래 명령은 후속 구현 후 사용할 계획이다.

```bash
env PYTHONDONTWRITEBYTECODE=1 "$T19_PYTHON" -m pytest -p no:cacheprovider tests/test_arp_generator.py tests/test_features.py tests/test_smoke.py -q
```

| 검사 묶음 | 검증할 내용 | 통과 조건 |
|---|---|---|
| 키·타입·경계 | EV·WB·채도 최소/최대 및 경계 밖, 잘못된 타입·중복·알 수 없는 키·비유한 수치 | 정상 입력 수용, 모든 결함 입력 거부. |
| 결합·입력 계약 | WB의 Camera/CustomTemp 분기, 필수값 누락, nullable 신호, unity WB, 요청과 무관한 도구 변경, 입력 불변 | 명시한 상태·오류와 프로필 생성 여부가 모두 일치. |
| 버전 | 헤더·스키마·구조화 결과·직렬화 결과 불일치, 헤더 부재·파싱 실패 | 런타임 호출·파일 기록·렌더 전 실패. 검사 중 저장소 헤더는 바꾸지 않고 임시 복사본 사용. |

| 스크립트 계약 | 생성 프로필 경로 인수, 미존재 입력·CLI, 비정상 종료·빈/잘못된 JPEG·옛 출력 | 거짓 성공 없이 실패. 실제 렌더 통과와는 별도 집계. |

20건의 요청·특성·예상 허용 키·방향성·WB 근거는 **첫 실제 호출 전에 고정**한다. 테스트 모듈의 작은 사례 표로 관리하며 별도 데이터 계층을 만들지 않는다.

| 요청군 | 건수 | 고정 사례 설계 |
|---|---:|---|
| 노출 단독 | 6 | 밝게/어둡게, 구체 EV 지정, 약한·강한 요청, T18 어두움 신호와 명시적 요청이 다른 경우. |
| WB 단독 | 4 | 촬영 WB 보존, 명시한 절대 Kelvin, Kelvin+Green, 근거가 있는 색온도 조정. CustomTemp 사례는 수치 기준을 입력에 명시. |
| 채도·생동감 단독 | 4 | 채도 증가/감소, 명시 수치, 생동감 조정. |
| 복합 요청 | 6 | 노출+채도 2건, 노출+WB 2건, WB+채도 1건, 세 도구 1건. WB 수치 근거를 각각 명시. |

WB 기준 누락·불가능한 범위·모순 지시·미지원 도구 요청은 별도의 거부 테스트에 둔다. 이를 성공한 프로필로 세어 90%를 채우지 않는다. 특성의 `null`·경고가 있어도 노출만 요청한 정상 사례는 가능하지만, 생성하지 못하면 해당 평가 건은 실패다.

실제 평가의 분모는 항상 20이다. 각 건의 최초 원시 응답·입력 해시·정규화 결과·선택 키·제약별 판정·버전·제공처·모델·프롬프트 버전·호출 횟수를 보존한다. 파싱 실패·런타임 오류·빈 출력·`needs_input`·프로필 미생성도 분모에 남긴다. 통과율은 `모든 키·제약·버전 검사를 통과한 건수 / 20`으로 계산한다. 18/20 이상을 요구하되 잘못된 프로필은 개별적으로 차단한다.

오프라인 모의 응답 테스트는 결정적 계약 검사용이다. 실제 런타임 20건은 별도로 실행하고 보존한 원시 응답을 pytest로 재검증한다. 요청한 방향과 선택 도구가 일치하는지도 별도로 기록해 형식 통과를 요청 충족이나 사진 품질 개선으로 확대 해석하지 않는다. 실행 환경 부재를 skip 처리한 결과로 완료를 선언하지 않는다.

## 8. ART-cli 실제 렌더 확인

1. Python·T18·버전 확인 후 저장소 루트에서 아래 명령으로 CLI를 빌드한다. `scripts/build_art_cli.sh`도 참조할 수 있지만 그 안의 `ENABLE_GUI=OFF`는 실제 CMake 옵션이 아니다. `-ffast-math`는 사용하지 않는다.

   ```bash
   cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
   cmake --build build --target art-cli -j 4
   ```

2. 빌드한 소스 커밋·헤더 PPVERSION·CLI 경로 및 바이너리 해시를 기록한다. 실행 파일만 보고 PPVERSION을 추측하지 않는다. 기존 빌드를 쓰려면 해당 소스·헤더와의 연결 근거를 확인하고, 확인할 수 없으면 재빌드한다.
3. 20건 중 모든 제약을 통과한 프로필 1개 이상을 선택한다. 사용한 요청 ID와 프로필 해시를 기록해 실제 생성 평가와 연결한다. `data/test_profile.arp`를 대신 넘기지 않는다.
4. `scripts/test_art_cli.sh`에 프로필 인수와 출력 디렉터리 인수를 추가하는 최소 변형을 계획한다. 인수 없이 실행하는 기존 사용법은 유지한다. T19 경로에서는 전용 임시 디렉터리를 사용하고, 임의 출력 폴더 전체를 삭제하지 않는다. 변수 경로는 인용하고 Bash의 `set -e`를 유지한다.
5. 변형 후 사용 예시는 `bash scripts/test_art_cli.sh "$T19_PROFILE" "$T19_OUT_DIR"`이다. 두 변수는 구현 검증 시 실제 생성 프로필과 새 임시 디렉터리의 절대 경로로 지정한다. 핵심 호출은 다음과 같다. `-c`는 마지막 옵션으로 둔다.

   ```bash
   build/rtgui/ART-cli -a -Y -j92 -o "$T19_OUT_DIR/sample1.jpg" -p "$T19_PROFILE" -c data/fivek_sample/sample1.nef
   ```

6. [공식 저장소 CLI 도움말](../rtgui/printhelp.h)의 중립값→`-p` 적용 순서를 따른다. `-d`·`-s`·`-S`를 넣지 않아 사용자 기본 프로필·sidecar가 선택 값을 덮지 않게 한다. 부분 `.arp`가 중립값 위에 적용된다는 근거도 같은 도움말에서 확인한다.
7. 실행 전에 해당 JPEG가 없음을 확인한다. 종료 코드·stdout/stderr·새 JPEG의 크기·실제 디코딩 성공·양의 가로세로 크기를 확인한다. 디코딩 검사는 기존 venv나 설치 도구로 수행하고 사용한 도구를 기록한다. 확장자나 파일 존재만으로 성공 판정하지 않는다.
8. RAW 해시와 원본 폴더의 파일 목록이 실행 전후 같은지 확인한다. 렌더 기록에 CLI·RAW·프로필·출력 해시와 검증 결과를 남긴다. 비정상 종료·출력 부재·빈/손상 JPEG는 실패이며 T19에서 자동 재생성하지 않는다.

최소 1개 성공은 형식·실행 경로의 근거다. 20개 전체 렌더 성공률, Lightroom과의 화질 동등성, GUI 동작 검증을 뜻하지 않는다. CLI 빌드나 실제 렌더가 막히면 키 검증 결과만 별도로 기록하고 T19 완료는 미충족으로 남긴다.

## 10. 커밋 분할

커밋은 아래 단위로 분리하며 모든 제목·본문은 국문으로 작성한다. 이번 작업은 계획 문서 작성에 한정하며 실제 코드 커밋은 수행하지 않는다.

1. **`docs: arp 구조화 생성기 구현 플랜 추가`** — 이 문서만 먼저 커밋한다. 제목은 이 문자열 그대로 사용한다.
2. `feat: arp 노출 생성과 버전 검증 추가` — 단계 2의 최소 경로 및 관련 테스트. 깨진 테스트만 먼저 남기지 않는다.
3. `feat: arp 화이트밸런스와 채도 생성 연결` — 단계 3과 20건 고정 사례·실제 런타임 연결 테스트.
4. `test: 생성 프로필 검증과 실제 렌더 확인` — 실제 20건 집계, 렌더 스크립트 변형·검증, 이 문서의 결과 기록 보완. 실행 증거 중 필요한 텍스트만 추적하며 임시 JPEG·인증 정보·바이너리는 커밋하지 않는다.

실제 생성 평가와 렌더가 끝나기 전에 성공을 전제로 완료 메시지를 작성하지 않는다. 첫 문서 커밋은 구현 변경과 섞지 않는다.

## 11. PPVERSION 충돌과 중단 조건

[§6의 해석](ART_live_param_feasibility.md#6-ppversion-정책-제안)에 따라 **도구 동작은 저장된 프로필의 해석·기본값·영상 처리 의미**를 가리킨다. 기존 키·타입·단위·처리 의미를 그대로 사용하는 외부 생성기와 이 계획 문서의 추가는 형식 변경이 아니므로 PPVERSION을 올리지 않는다. 근거는 코어·헤더 변경 없음, 기존 키·열거값의 대조, 선택 값의 직렬화 왕복과 실제 CLI 검증으로 남긴다.

다음 중 하나라도 발생하면 생성·파일 기록·렌더 또는 완료 판정을 해당 지점에서 중단한다.

- 조사 기준 `1045`, 현재 헤더, 스키마 지원 버전, 생성 객체·파일 버전 중 하나라도 다름. 새 헤더 값에 자동으로 맞추거나 오래된 파일의 Version만 바꿔 재사용하지 않는다.
- 헤더를 읽을 수 없거나 실제 렌더 바이너리의 소스·버전 근거를 확보하지 못함. 먼저 같은 소스의 빌드 근거를 복구한다.
- 문서 키와 실제 저장·로드 키의 충돌, WB 열거값·타입·단위·결합 규칙의 근거 불일치. 소스 근거와 계획을 정정한 뒤 검사를 다시 수행한다.
- 지원을 위해 `.arp` 형식·기본값·해석, 영상 처리식·순서를 바꾸거나 `rtengine/`·`rtgui/` 수정이 필요해짐. T19에서 예외를 확대하지 않고 별도 설계·호환 정책·PPVERSION 판정을 거친다.
- T18 계약·RAW 해시·런타임이 준비되지 않음, 실제 20건에서 18건 미만 통과, 실제 렌더 0건. 해당 실패를 기록하고 T19 완료를 선언하지 않는다.

헤더만 새 버전으로 바뀐 경우에도 차이를 검토하고 스키마·검증·CLI 빌드 근거를 함께 갱신한 뒤 재개한다. PPVERSION 증가는 생성기의 오류를 숨기는 수단으로 사용하지 않는다.

## 12. 구현과 인수 기록

구현·검증일: 2026-11-05~2026-11-07. 이 절은 최초 구현 당시의 실제 실행 기록이다. 당시 실제 생성 20/20·렌더 1건·전체 pytest 1298 passed를 확인했으나, 후속 검토에서 요청 해석과 기록 검증의 누락을 발견했다. 해당 결함과 최신 인수 근거는 §13에 기록한다.

### 구현 계약과 사용법

`src/artagent/arp/schema.json`은 기존 PPVERSION **1045**의 노출·WB·채도·생동감 부분 프로필을 정의한다. `generator.py`는 T18 계약 검사, 요청별 허용 키 결정, 구조화 제안 검증, 결정적 INI 직렬화·재파싱을 담당한다. `runtime.py`는 기존 제공처의 단일 호출과 실행 증거 검사를 분리한다. 계획 당시 생성기 내부에 둘 예정이던 런타임 처리는 답변 모듈과 결합하지 않고 독립 검증하기 위해 작은 별도 파일로 나눴다.

공개 함수는 `generate_profile(request, features, runtime=..., header_path=...)`, `validate_profile`, `serialize_profile`, `parse_profile`이다. 생성 함수는 파일을 쓰지 않고 `status`와 결과를 반환한다. 성공 상태는 `ok`, 실패 상태는 `validation_error`·`runtime_error`·`needs_input`·`unsupported_request`다. CLI가 검증된 성공 결과만 새 `.arp`에 기록하며 기존 출력·RAW·표준 sidecar 경로를 덮어쓰지 않는다.

초기 요청 해석은 한국어·영어의 노출/밝기·WB/색온도·채도/생동감 용어로 한정한다. 명시한 도구·키 외의 제안은 거부한다. 처리할 수 없는 부정 지시나 WB 상대량은 `needs_input`으로 반환한다. 예를 들어 `색온도를 2000K 낮춰줘`는 절대 온도 2000K로 바꾸지 않는다. `WB 5500K`는 절대 온도, Green을 생략하면 중립값 1.0을 명시한다. T18의 계수를 Kelvin으로 환산하지 않는다. `촬영 WB 유지`는 Camera 방식으로 처리한다. 세션 증분 수정과 실패 피드백 재생성은 포함하지 않았다.

Python **3.14.3**의 기존 프로젝트 venv를 사용했다. 소비 시 설치를 확인한 기존 패키지는 jsonschema **4.26.0**, pytest **9.1.1**, NumPy **2.5.3**이며 새 패키지는 설치하지 않았다. JPEG 검증에는 기존 libjpeg-turbo **3.2.0**의 `djpeg`를 사용한다. 렌더 스크립트 테스트의 작은 JPEG 준비에는 같은 설치의 `cjpeg`를 사용한다.

실제 사용한 런타임은 코드 기본값을 승계한 **codex-cli 0.166.0 / gpt-5.6-sol**이다. 제공처·모델 환경변수는 미설정이었다. 임시 작업 폴더·읽기 전용 모드·사용자 설정 무시·셸 도구와 웹 검색 비활성화를 적용하며, 반환 이벤트·최종 파일·정상 종료·호출 1회 증거를 대조한다. 다른 제공처로 자동 전환하지 않는다. 기존 명시적 호환 API 분기도 지원하며 응답 형식·종료·도구 호출 거부는 모의 응답으로 검증했다. 호환 API의 실제 호출은 이번 인수 범위가 아니다.

샌드박스 내부에서는 런타임 초기화가 `Operation not permitted`로 실패했다. 해당 기록은 `build/t19-checks/sandbox-first/`에 보존했고 완료 근거에 포함하지 않았다. 이후 허용된 실행 환경에서 실제 평가를 수행했다. 최초 `live-v1`의 20/20 결과도 보존하되 최종 소스의 인수 근거는 보완 후 새 실행인 `live-v2`로 한정한다.

```bash
T19_PYTHON=/Users/user/Workspace/Programming/Projects/AAART/venv/bin/python3
env PYTHONPATH=src PYTHONDONTWRITEBYTECODE=1 "$T19_PYTHON" -m artagent.arp.generator \
  --request '노출 +0.5 EV, WB 5200K, 채도 +10, 생동감 +5' \
  --features data/eval/t19/live-v2/features.json --output /tmp/t19-example.arp
env T19_PYTHON="$T19_PYTHON" PYTHONDONTWRITEBYTECODE=1 \
  bash scripts/test_art_cli.sh /tmp/t19-example.arp /tmp/t19-render
```

`/tmp/t19-example.arp`는 존재하지 않는 새 경로여야 한다. 렌더 스크립트는 인수 없는 기존 실행법도 유지한다. 프로필을 명시하면 현재 스키마·헤더 버전을 먼저 검사하며 `ART_CLI_PATH`, `ART_RAW_FILE`, `T19_PYTHON`으로 실행 환경을 명시할 수 있다. JPEG는 새 임시 폴더에서 생성·전체 디코딩한 뒤에만 출력 경로로 옮긴다. 옛 JPEG·빈 파일·손상 파일·비정상 종료로 성공 판정을 만들 수 없으며 실패 시 기존 JPEG를 보존한다.

### 검증 범위와 버전 판정

구현 전 실패를 확인한 테스트를 추가한 뒤 정상·경계·거부 경로를 구현했다. 별도 코드 검토에서 확인한 EXIF 타입, boolean bin 경계, 매우 큰 정수, 변경 금지 지시, 상대 WB 기준, API의 잘못된 message 구조, 저장된 실행 증거와 평가 중단 조건을 보완했다. 실행 기록의 통과 플래그를 신뢰하지 않고 재검증하며, 단일 JSON 실패는 분모에 남긴 채 다음 요청을 처리한다. 환경 준비 실패만 조기 중단하고 미실행 사례를 성공으로 세지 않는다.

관련 검사 **202 passed**를 확인했다. 여기에는 20건 기록의 재생 검증, 실행 증거 변조 거부, 첫 응답 결함 시에도 20건을 시도하여 19/20을 집계하는 검사가 포함된다. 오프라인 모의 검증은 실제 생성 통과율과 별개다.

ART-cli는 이 작업 폴더에서 Release·아웃오브소스로 빌드했다. 바이너리의 빌드 기준은 `8d7efb27c`이며, 이후 생성기 커밋과 비교해 `rtengine/`·`rtgui/`·`cmake/`·최상위 CMake 변경이 없음을 확인했다. 바이너리 SHA-256은 `ef53085775d14bf34427f096a1aba4c20279d97643eca47b36803606112940fd`다. 코어·프로필 형식·기존 도구 의미를 변경하지 않았으므로 **PPVERSION은 1045를 유지**한다.

실제 렌더는 원래 출력과 측정 조건이 다른 T18 통계의 일치 검사가 아니다. 예비 C06 렌더의 JPEG 실측 크기는 **2006×3031**이었다. 사용자 프로필 디렉터리 부재 진단이 stderr에 있었으나, 명시한 프로필 적용·종료 코드 0·새 JPEG의 전체 디코딩 성공을 확인했다. 이 진단을 숨기거나 GUI 지원 검증으로 확대하지 않는다.

### 최종 실제 생성·렌더 결과

## 13. 재검토 결함 보완과 최신 검증

검토에서 정상 경로 외의 입력 해석·증거 검사 누락을 재현했다. 최초 20건 성공과 전체 테스트 통과만으로 이들 경로까지 검증되었다고 판단한 점을 정정한다. 요청 해석과 평가 기록 검증을 각각 별도 수정 커밋으로 분리했다.

| 결함 | 보완한 동작·회귀 검증 |
|---|---|
| 보존 지시의 도구 이름을 변경 권한으로 해석 | `채도 변경 없이`·`without changing saturation`를 보존 대상으로 처리한다. `채도와 생동감`·`saturation, or the vibrance`처럼 병렬로 나열한 대상도 모두 보존하며, 모순·불명확한 부정 표현은 추가 입력을 요구한다. 보존 도구를 포함한 제안은 거부한다. |

## 14. 명시한 수치와 제안값의 일치 검증

추가 검토에서 `노출 +0.5 EV` 요청에 `-2 EV`, `채도 12` 요청에 `-50`을 제안해도 형식·범위 검사만 통과하면 정상 처리하는 누락을 확인했다. **eaee6ddd4**에서 요청 수치 계약을 추가하고, 모델의 잘못된 제안이 `.arp`로 출력되지 않도록 보완했다.

- `contract.exact_values`에 명시한 노출·채도·생동감의 절대 목표값을 기록하고 제안값과 직접 대조한다. 명시값과 다른 값은 `validation_error`이며 정상 프로필을 반환하지 않는다. 값이 같은 `0.5`·`.5`·지수 표기는 허용한다.
- 입력값 자체의 범위·타입도 호출 전에 검사한다. 노출 13 EV, 채도 101, 생동감 -101, 비정수 채도, 비유한 수치는 거부한다. 여러 목표값·범위·증분 기준이 불명확하면 `needs_input`으로 반환한다. 클램프나 첫 숫자 선택으로 요청을 바꾸지 않는다.
- EV 단위만 적은 요청도 같은 검사를 거친다. `1e EV`·`.5.5EV`·잘못된 단위 접미사는 오류이고, `0.3~0.5EV`·`0.5 EV 또는 1`은 추가 입력을 요구한다. `채도 12 EV`를 노출 12 EV로 추가 해석하지 않는다. `채도 12, +0.5EV`처럼 구분한 복합 요청은 각 도구에 값을 연결한다.
- 숫자 없는 명확한 방향은 `contract.directions`로 검사한다. 단일 프로필의 중립값 0을 기준으로 밝게/올려줘·어둡게/줄여줘의 부호를 확인한다. 도구 앞의 `increase/reduce`도 그 도구에 연결하고 이전 도구나 WB의 지시로 오인하지 않는다. 명시한 절대값이 있으면 그 값을 우선한다. 기존 세션의 증분은 T21 범위다.

이 계약은 프롬프트 버전 **t19-profile-v3**로 구분한다. `.arp` 키·타입·영상 처리 의미와 엔진 코드는 변경하지 않아 **PPVERSION 1045**를 유지한다. 새 패키지는 설치하지 않았다.

누락을 재현하는 실패 테스트부터 추가한 후 구현했다. 관련 검사 **292 passed**, 별도 숫자 해석 재현 검사 **20건 통과**를 확인했다. 이 결과는 명시 수치·지원 방향 표현의 검증이며 모든 자연어 의도의 완전한 이해나 화질 개선 보증을 뜻하지 않는다.
