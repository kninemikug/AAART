### 3.1 보호 대상 구성

`validate_record_path()`가 보호 목록을 구성할 때 다음 세 루트를 사용한다.

## 4. 보완할 계약 B — 실행 정책과 성공·실패 trace 일치

### 4.1 실행 조건 고정

기존 임시 작업 폴더, `--ephemeral`, `--json`, `-o`, `--ignore-user-config`, `--sandbox read-only`를 유지한다. 사용자 설정 무시와 read-only sandbox는 shell/exec·웹 검색을 비활성화하는 설정을 대신하지 않는다. 공식 설정의 비활성화 값은 아래와 같으며, 설치 CLI 버전의 지원 여부를 실행 전에 확인한다. [Codex 설정 참조](https://learn.chatgpt.com/docs/config-file/config-reference)

| 대상 | 실제 실행에 넣을 설정 | trace 대조 기준 |
| --- | --- | --- |
| shell | `features.shell_tool=false` | 명령의 `-c` 설정 또는 동등한 `--disable shell_tool`과 일치 |
| exec | `features.unified_exec=false` | 명령의 `-c` 설정 또는 동등한 `--disable unified_exec`과 일치 |
| 웹 검색 | `web_search="disabled"` | TOML 문자열 값이 포함된 `-c` 인자와 일치 |
| MCP | 자동 로드되는 설정을 차단하고, 남는 서버가 있으면 해당 `mcp_servers.<id>.enabled=false` 적용 | 설정 출처와 실제 비활성화한 서버 ID를 기록; 확인하지 않은 전역 비활성화 플래그를 만들지 않음 |

최소한의 내부 정책 값에서 실행 명령 인자와 `generation.trace.execution_policy`를 함께 구성한다. 그 값을 `validate_codex_execution()`의 성공·실패 trace 생성까지 전달하고 검증 함수 안에서 정책을 상수로 재작성하지 않는다. 기록에는 실제 전달한 설정 키·값과 설정 출처를 남긴다. 전체 프롬프트나 자격증명을 포함한 명령 문자열을 중복 저장하지 않는다.

`tools_enabled`를 유지한다면 확인된 비활성화 설정의 적용 결과에서만 산출한다. 설치 버전의 다른 도구 출처가 남거나 적용 여부가 미확인이면 전부 꺼졌다고 기록하지 않고 해당 요약값을 null로 두며, 필요한 실행 조건을 충족할 때까지 배치를 시작하지 않는다. `validation.additional_tool_count=0`은 관찰 결과로 별도 기록한다. 로그에서 호출이 없었다는 사실로 도구 설정을 추론하지 않는다. 설정을 거부한 시작 실패에서는 요청한 정책과 적용 여부를 구별한다.

### 4.1.1 요청 설정과 적용 확인 상태

공통 정책 생성 시 `config_overrides`와 `config_source`에는 실제 명령에 전달할 요청 설정만 넣는다. 요청 단계에서 적용 결과를 `tools_enabled=False`로 확정하지 않는다. 새 trace v2에 `execution_policy.application_status`를 추가하고 다음처럼 기록한다.

| 상황 | `application_status` | `tools_enabled` |
| --- | --- | --- |
| 실행 전 또는 설정 적용 여부 미확인 | `unconfirmed` | null |
| 미지원 옵션·설정 오류, 비정상 종료, 시간 초과, 이벤트 검증 실패 | `unconfirmed` | null; 실제 CLI 진단과 실패 원인은 보존 |
| 설치 버전의 설정 호환성과 도구 출처를 확인하고, 정상 종료·기존 성공 검증까지 통과 | `confirmed` | 실제 비활성화 설정을 확인한 경우에만 false |

비정상 종료 뒤 시작 이벤트가 있거나 도구 호출이 보이지 않는다는 이유로 confirmed를 지정하지 않는다. null은 적용 여부를 확정하지 못했다는 뜻이며, 도구가 활성화됐다는 뜻도 아니다. 성공·실패 trace에는 각 실행의 정책 사본을 전달하여 다른 실행의 확인 상태가 섞이지 않게 한다. 설정 오류가 나면 요청한 키·값과 stdout/stderr를 유지한 채 종료한다. 같은 생성 요청의 재호출은 하지 않는다.

적용 확인 상태는 실제 생성 호출에서만 갱신한다. 저장된 로그를 다시 검증하는 것만으로 현재 정책이 실제 적용됐다고 확정하지 않는다. 이벤트 검증 함수는 전달받은 적용 상태를 보존하며 도구 항목 0개나 로그 검증 통과를 정책 적용 증거로 대체하지 않는다.

기존 `test_codex_unsupported_option_failure_preserved`의 `tools_enabled is False` 기대값을 `is None`과 `application_status=unconfirmed`로 바로잡는다. 테스트를 삭제·skip하거나 실패 기록의 정책 필드를 제거하여 통과시키지 않는다. 정상 명령·정책 대조 테스트에는 confirmed와 false 조건을 함께 확인한다.

현재 설치 CLI의 도움말에서 `--ignore-user-config`, `--ignore-rules`, `--sandbox`, `--json`을 확인했다. 인증 정보는 기존 방식으로 재사용하고 사용자 전역 설정 파일 자체를 수정하지 않는다. `--ignore-rules`를 사용할 경우 명시적 sandbox·도구 비활성화 설정과 함께 적용하고, 사용한 정책을 기록한다. [비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)

`-c`·`--disable`의 존재만으로 개별 설정의 지원을 확정하지 않는다. 옵션·설정 오류가 나면 확보한 stdout/stderr와 원인을 기록하고 종료한다. 옵션을 몰래 제거하거나 다른 제공처로 전환하지 않는다.

임시 작업 폴더와 read-only 정책만으로 절대경로 읽기가 완전히 차단됐다고 주장하지 않는다. 성공 판정에는 아래의 이벤트 검증도 반드시 적용한다. 이 절의 설정은 추가 도구 사용을 줄이는 실행 조건이며, 성공 로그를 대신하지 않는다.

### 4.2 T11 성공 이벤트 계약

최신 구현에서 통과한 계약을 유지한다. `--json` stdout의 모든 비어 있지 않은 줄을 JSON 객체로 파싱한다. JSON 형태처럼 보이는 줄만 골라 읽거나 파싱 예외를 무시하지 않는다.

| 항목 | 성공 조건 및 거부 조건 |
| --- | --- |
| 로그 존재·구조 | 비어 있지 않고 모든 비어 있지 않은 줄이 유효한 JSON 객체이며 이벤트 `type`이 있음; 빈 로그·잘린 JSON·일반 텍스트·잘못된 구조는 거부 |
| 생명주기 | `thread.started`, `turn.started`, `turn.completed`가 순서대로 확인되고 시작·완료 turn이 각각 1회; 미완료·중복 turn은 거부 |
| 오류 | `turn.failed`, `error` 또는 비정상 프로세스 종료는 거부 |
| 항목 이벤트 | 설치 CLI에서 확인한 `item.started`, `item.updated`, `item.completed`를 처리; 항목 유형이 없거나 알 수 없는 유형이면 거부 |
| 허용 항목 | `agent_message`, `reasoning`만 허용. 다른 유형을 허용해야 한다면 실제 CLI 계약을 확인하고 근거와 테스트를 먼저 남김 |
| 추가 도구 | 명령 실행, 파일 변경, MCP, 웹 검색 및 기타 도구 항목은 시작·갱신·완료 중 어느 위치에 있어도 거부 |
| 최종 답변 | 완료된 최종 `agent_message`가 있고, 그 메시지와 `-o` 파일을 같은 JSON 파서로 읽었을 때 `answer`·`citation_ids`가 일치 |
| 알 수 없는 이벤트 | 조용히 건너뛰지 않고 검증 오류로 기록; 이후 자동 재시도 없음 |
| 사용량 | `turn.completed`가 제공한 usage를 보존. 없는 값은 null; 텍스트 정규식 결과로 이벤트 검증 실패를 보충하지 않음 |

이벤트 검증 실패 후 인용 검증이나 성공 출력으로 진행하지 않는다. 정상 이벤트를 확인한 뒤 기존 답변 JSON·인용 검증을 그대로 적용한다. 추가 도구 사용 판정은 사후 탐지이므로 실제 사용이 있었다면 실패 기록에 남긴다.

### 4.3 실행 기록의 보존 계약

별도 이벤트 파일 대신 각 실행의 `generation.trace`에 CLI stdout과 검증 결과를 함께 저장한다. 이번 수정은 기존 수치의 null 허용과 정책 적용 상태를 명시하므로 새 trace는 v2로 기록하고 기존 v1은 읽기 호환을 유지한다. 바깥 실행 기록 형식은 유지한다. 기존 로그가 없는 기록에 빈 trace를 붙여 새 검증을 통과한 것처럼 처리하지 않는다.

| `generation.trace` 필드 | 명세 |
| --- | --- |
| `trace_schema` | 신규 trace는 `t11-codex-trace-v2`; 기존 `t11-codex-trace-v1` 기록은 그대로 보존하고 읽기 지원 |
| `cli_version`, `process_returncode` | 실행 CLI 버전과 실제 종료 코드; 시간 초과 등 미확인 값은 null |
| `execution_policy` | §4.1의 공통 요청 설정과 §4.1.1의 `application_status`·`tools_enabled`. 미확인 적용은 unconfirmed·null. 자격증명 제외 |
| `stdout_jsonl` | 수신한 전체 이벤트 스트림; 순서·실패 줄·미지 이벤트도 보존 |
| `stderr` | 실패 원인 대조에 필요한 CLI 진단; 자격증명 제외 |
| `process_error` | 기존 필드를 유지. 프로세스 오류가 없으면 null; 시간 초과는 `kind=timeout`, 실제 `timeout_seconds`를 기록 |
| `validation` | `status`(verified/rejected/unavailable), 이벤트 개수, thread ID, 시작·완료 turn 개수, 관찰 항목 유형, 추가 도구 항목 이벤트 개수, 오류 줄·사유. v2에는 §4.3.2의 `summary_status`·`summary_error`를 기록; 미집계 수치·목록은 null |

파싱한 이벤트 배열은 검증 중에 사용하고 원본 stdout에서 다시 만들 수 있게 한다. 답변 텍스트가 포함된 이벤트를 기록에서 제거하지 않는다. 로그에 비밀값이 있다면 그 값만 제거하고 제거 여부를 표시하며, 검증에 필요한 이벤트 종류·순서·구조는 유지한다.

생성 함수가 예외를 던지는 경우에도 수집한 trace를 `run_pipeline()`의 오류 기록으로 전달한다. 최소한의 내부 예외 데이터 전달 방식을 사용하고 전역 변수에 실행 상태를 저장하지 않는다. 비정상 종료·시간 초과는 확보한 부분 stdout/stderr를 남기며 시간 초과 처리는 아래 계약을 적용한다. 기존 trace의 재검증에서는 선택 필드 `process_error` 누락을 null로 해석할 수 있다.

`generation.call_count=1`은 해당 생성 호출을 시도했다는 뜻이다. trace 실패 실행은 `execution.status=error`, `failed_step=generation`, 0이 아닌 종료 코드로 기록하고 성공한 대표 질문으로 세지 않는다. 성공 실행에서 CLI가 제공하지 않는 temperature·finish reason은 계속 null로 둔다. 실패 실행의 기존 로컬 오류 표시는 CLI에서 받은 finish reason으로 보고하지 않는다.

### 4.3.1 시간 초과 로그 정규화와 실패 판정

Python의 `TimeoutExpired.stdout`/`output`과 `stderr`는 `text=True`인 실행에서도 bytes일 수 있다. 최신 구현에서 통과한 정규화 규칙을 정상 종료와 예외 경로 모두에서 유지한다. [Python 3.14 subprocess 문서](https://docs.python.org/3.14/library/subprocess.html#subprocess.TimeoutExpired)

| 수신값 | trace에 전달할 문자열 |
| --- | --- |
| str | 내용을 그대로 유지 |
| bytes | UTF-8로 디코딩; 잘린 다중 바이트나 잘못된 바이트는 `errors="replace"`로 표시하고 나머지 내용 유지 |
| None | 빈 문자열; 출력 미수신으로 취급 |

bytes를 `str(value)`로 바꿔 `b'...'` 표현을 기록하거나 빈 문자열로 버리지 않는다. 디코딩을 이유로 줄·진단을 삭제하거나 이벤트를 고쳐 정상 JSON으로 만들지 않는다. stdout과 stderr에 각각 같은 규칙을 적용한다.

시간 초과는 답변 파일이나 완료 이벤트가 있어도 생성 실패다. `process_returncode=null`, `process_error.kind=timeout`, 실제 제한 시간(현재 120초)을 기록하고 `validation.error_reason`에 시간 초과와 이벤트 오류가 있다면 그 원인도 남긴다. 부분 stdout 또는 stderr가 있으면 `validation.status=rejected`로 보존하며, 둘 다 수신되지 않은 경우에만 unavailable로 둔다. 디코딩된 부분 로그를 `GenerationError.trace` → 파이프라인 오류 기록 → 안전한 CLI `--record` JSONL까지 전달한다. 시간 초과를 확인하려고 실제 LLM을 120초 기다리는 테스트는 하지 않는다.

### 4.3.2 실패 로그도 집계하고 미집계 값은 null로 기록

정규화한 stdout/stderr를 확보한 뒤 이벤트를 검사하고 집계 결과를 만든다. 시간 초과·비정상 종료의 최종 실패 판정은 유지하되, 그 판정으로 집계 전에 반환하여 초기값 0을 기록하지 않는다. 기존 이벤트 해석을 재사용하는 최소 내부 함수로 충분하며 별도 실행 프레임워크나 로그 저장소를 추가하지 않는다.

| 수신 로그의 분석 상태 | `validation.summary_status` | 집계 필드 계약 |
| --- | --- | --- |
| 수신한 모든 비어 있지 않은 줄의 이벤트 구조·항목 유형을 분석할 수 있음 | `complete` | `event_count`, thread ID, 시작·완료 turn 수, `observed_item_types`, `additional_tool_count`를 실제 관찰값으로 기록 |
| 잘린 JSON·비JSON·구조 오류·해석 불가 이벤트가 있음 | `partial` | 문제 줄과 원인을 `summary_error`에 표시. 전체 집계를 확정할 수 없는 수치와 목록은 null로 기록; 원본 전체 로그 보존 |
| 이벤트 stdout 미수신 또는 이벤트 분석을 수행할 수 없음 | `unavailable` | 미집계 수치·목록은 null. stderr만 있어도 진단은 보존; 미분석을 0개로 표시하지 않음 |

complete는 **수신된 로그를 전부 분석했다**는 뜻이다. 모델 turn 완료나 실행 성공을 뜻하지 않는다. `additional_tool_count`는 금지된 항목 이벤트의 수로 집계하고, 같은 항목의 시작·갱신·완료 이벤트도 각각 센다. 도구 호출 횟수로 해석하지 않는다. 모든 줄을 분석하여 도구 항목이 없음을 확인한 경우에만 0을 기록한다. 분석 중 도구나 오류 이벤트를 발견해도 뒤에 수신된 로그의 집계를 버리지 않는다.

`summary_error`는 문자열 또는 null이다. partial이면 문제 줄 번호와 분석 불가 원인을 기록한다. complete이면 집계 오류는 null로 두며, 발견한 도구·모델 오류 등 검증 실패는 별도로 유지한다. complete의 수치는 정수, 관찰 유형은 문자열 목록으로 기록한다.

검토 재현 입력인 `thread.started`(thread ID 포함) → `turn.started` → `item.updated`(web_search)에서는 시간 초과와 종료 코드 2 모두 이벤트 3개, 시작 turn 1개, 완료 turn 0개, 도구 항목 이벤트 1개와 해당 thread ID를 기록해야 한다. `validation.status=rejected`와 프로세스 실패 원인은 유지한다.

프로세스 오류를 `validation.error_reason`의 주된 실패 원인으로 남기고, 추가 JSON·항목 오류는 `summary_error`에도 기록한다. 집계 오류가 원래 시간 초과·종료 코드를 덮거나 raw trace 전달을 막지 않게 한다. 완료 이벤트와 정상 답변 파일을 발견해도 시간 초과·비정상 종료를 성공으로 승격하지 않는다. 성공 경로에서는 §4.2의 엄격한 검증을 그대로 적용하며, partial·unavailable 집계를 성공 근거로 사용하지 않는다.

### 4.4 필수 회귀 테스트

Codex 프로세스는 모의 실행으로 대체하고 답변 파일과 이벤트는 테스트용 임시 디렉터리에 생성한다. 단위 테스트에서 실제 LLM을 호출하지 않는다.

| 입력 | 기대 결과 |
| --- | --- |
| 실행 명령 인자 캡처 + 정상 이벤트 | shell/exec·웹 비활성화 인자와 MCP 조건이 실제 적용되고, trace의 키·값이 같은 정책과 일치; 검증 함수의 고정 정책으로 대체되지 않음 |
| 미지원 옵션·설정으로 모의 시작 실패 | 요청 설정을 유지하면서 application_status=unconfirmed·tools_enabled=null·종료 코드 2·진단을 기록; 생성 시도 1회, 자동 재호출 없음 |
| 정상 이벤트 + 일치하는 최종 답변 | 성공; trace가 최종 JSONL에 남고 다시 파싱·검증 가능 |
| 빈 stdout + 정상 답변 파일 | 생성 오류; 성공으로 처리하지 않음 |
| 잘린 JSON·비JSON 줄·필수 필드 누락 + 정상 답변 파일 | 생성 오류; 문제 줄과 trace 보존 |
| 완료 이벤트 누락·turn 중복·오류 이벤트 | 생성 오류 |
| command/file-change/MCP/web-search 항목 | 생성 오류; 추가 도구 판정과 원본 이벤트 보존 |
| 도구 항목이 `item.updated`에만 나타남 | 생성 오류 |
| 이벤트의 최종 답변과 `-o` 파일 불일치 | 생성 오류 |
| 프로세스 비정상 종료 | 생성 오류; 확보한 부분 로그 보존 |
| 유효한 3개 이벤트(thread 시작·turn 시작·web_search 갱신) + 시간 초과 | rejected·summary complete; 이벤트 3개·시작 1개·완료 0개·도구 이벤트 1개·thread ID와 timeout 원인 보존 |
| 같은 3개 이벤트 + 종료 코드 2 | 위 집계를 유지하고 비정상 종료 원인 기록; 정책 적용은 unconfirmed·null |
| 유효한 이벤트 뒤에 잘린 JSON 또는 미지·구조 오류 이벤트 | partial·summary_error·문제 줄 보존; 확정하지 못한 집계는 null; 프로세스 오류도 보존 |
| stderr만 있고 이벤트 stdout은 None·빈 문자열 | 진단 보존·summary unavailable·미집계 null; 도구 이벤트 0개로 확정하지 않음 |
| `TimeoutExpired(output=부분 이벤트 bytes, stderr=진단 bytes)` | 디코딩된 두 로그가 유지되고 rejected·시간 초과 원인·null 종료 코드가 저장됨 |
| 시간 초과 로그가 str·None·빈 bytes인 경우 | str은 유지; 양쪽 출력 미수신일 때만 unavailable; 모두 생성 실패 |
| 시간 초과 로그의 UTF-8 끝이 잘렸거나 잘못된 바이트 포함 | 디코딩 예외로 trace가 사라지지 않음; 나머지 로그와 대체 문자를 보존하고 실패 |
| 완료 이벤트·정상 답변 파일이 있으나 시간 초과 발생 | 성공으로 승격하지 않음 |
| 완료 이벤트·정상 답변 파일 + 종료 코드 2 | 이벤트 집계는 유지하고 생성 실패; 성공 stdout 없음 |

## 6. 기존 15개 성공 기록 보존과 최종 합격 기준

이번 수정은 실패 기록 메타데이터와 집계를 바꾸므로 새 LLM 실행은 필수가 아니다. 기존 `docs/T11_execution_records.jsonl` 15개를 유지한다. 현재 파일의 SHA-256은 `5d3d9a7df432cbfac741d479c554aae69a6dfbc8039ed166331d7f5a8d1b64b7`이며 후속 검증에서 같은 지문을 확인한다.

새로 생성하는 trace는 v2로 기록하고 `application_status`, `summary_status`, `summary_error`와 집계의 null 허용을 명시한다. 기존 15개 trace v1은 읽기 지원한다. v1에 없는 적용 상태는 unconfirmed, 없는 집계 분석 상태는 null로 해석하고 그 값을 확인 완료로 채워 저장하지 않는다. 기존 필드와 원본 이벤트를 읽어 이전 성공 판정을 재현하며 v2 필드가 없다는 이유만으로 기존 기록을 거부하지 않는다. 독립 재검증에서 버전 표식·새 필드는 별도 계약으로 검사하고, 이전 필드의 실제 관찰값·답변·usage를 대조한다. v1 입력과 재검증 출력 전체를 단순 동등 비교하여 실패시키지 않는다.

### 6.1 검토 메모의 정합성
