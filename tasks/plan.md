# Implementation Plan: Phase A — ④ ART Master Agent (2026-09-01 ~ 10-01)

## Overview

WBS(`docs/ART_agentic_wbs.md` §5, A-01~A-26)의 엔지니어링 실행판. ④ ART Master Agent — 처리 경로 분기 → 근거 검색(RawPedia·Issues) → 인용 답변, 실행 요청 → .arp 생성 → ART-cli 렌더링 폐쇄 루프를 **10/1 중간발표에서 시나리오 4단계 데모**로 완성한다. Phase B(①)는 중간발표 이후 rolling-wave로 별도 계획한다(FiveK 승인·태깅 게이트 결과가 선행해야 관찰 오류가 없음).

**Task list target: `tasks/todo.md`** — 프로젝트에 지정된 외부 트래커 없음(AGENTS.md 무관련). 각 태스크 카드에 WBS 코드(A-XX)를 병기해 역추적 가능.

## Architecture Decisions

- **커밋 및 PR 언어 원칙**: 모든 커밋 메시지와 PR 제목·설명은 국문(한국어)으로 작성한다.
- **패키지 레이아웃**: `src/artagent/` + `tests/` 신규. 데이터 수집·청킹 프로그램의 위치와 파일명은 각 태스크 구현 시 결정한다. 루트 venv(Python 3.14) 재사용.
- **의존 관리**: 증분식 — 소비 태스크가 필요할 때 pip 설치 + 설치 기록 문서에 append. 목록 파일화(pyproject 등)는 의존성이 실제로 쌓인 뒤(T8~T13 경) 기록을 옮기는 형태로 그때 결정한다. 미리 만들지 않는다.
- **Vertical slicing**: 9/1~9/11은 수집·질문셋·검색 기반을 만드는 확정 구간이다. 그 뒤 직선 답변 경로 → 라우터·강화 검색 → 프로필 루프 → 평가·데모 순으로 연결한다.
- **검색·청킹**: 검색 저장소는 Chroma로 고정한다. T4의 RawPedia 원문과 T10-2a의 정제 GitHub 후보를 T8-1 질문셋으로 연결한다. T8-2는 두 출처를 각각의 구조에 맞게 청킹하고, 같은 임시 Chroma에서 청킹·임베딩 조합을 비교한다. 청킹 규칙·글자 수·오버랩·직렬화 형식·임베딩 후보는 미리 정하지 않는다. 청크에는 본문, 구분 가능한 식별자, 원문 또는 후보 항목 식별자, 원문 위치가 있어야 한다. 비교는 출처별 Hit@k·MRR@k와 두 출처 평균, 실행 부담을 기록해 한 조합을 고른다. T9는 9/9~10에 공통 적재·검색 경로를 만들고, 9/11 T8-2의 선정 결과를 적용해 실제 저장소를 구성한다. 현재 선정값은 [재현 인계](../docs/T08_2_t9_handoff.md)에 고정된 T9 초기 검색 기준점이다. 답변 생성은 T11, 리랭킹과 k 튜닝은 T15에서 다루고, 실제 답변 품질을 반영한 최종 스택은 T15·T17 이후 별도 게이트에서 선정한다.
- **9/1~9/11 흐름**: 김구는 프로젝트 베이스를 만든 뒤 수집 문서 질문셋과 벡터DB 공통 경로를 담당한다. 김대성은 RawPedia 원문 수집 뒤 두 출처 문서의 청킹·임베딩 모델 시험을 담당한다. 고태우는 GitHub 원문 수집·정제 뒤 LangGraph 상태·노드·전이 설계를 담당한다. 9/11에는 T8-2 선정 결과를 T9 실제 저장소에 적용한다.
- **검색 평가 근거**: 검색 단계와 답변 생성 단계는 분리해 평가한다. 검색 결과와 기준 문서 ID를 비교하는 방식은 [LlamaIndex Retrieval Evaluation](https://llamaindex.openml.io/python/framework/understanding/evaluating/evaluating/) 및 [RAGAS ID-based Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)에, 두 단계를 나눠 평가하는 방식은 [LangSmith intermediate-step evaluation](https://docs.langchain.com/langsmith/evaluate-on-intermediate-steps)에 근거한다.
- **처리 경로 분기**: T13-1은 9/8~9/11에 주제 라벨이 아니라 다음 처리 경로를 고르는 상태·노드·전이 규칙과 20개 경로 라벨을 설계한다. 문서 질문은 RawPedia 검색, 문제 해결은 Issues·Discussions 검색, 실행 요청은 프로필 생성·ART-cli 렌더링으로 보낸다. T13-2는 그 설계를 구현한다.
- **W3 병렬 착수**: T14의 재작성·HyDE 구현·평가는 T8-1 질문셋과 T9 검색 모듈로 시작한다. T13-2가 T13-1 설계를 받아 라우터를 구현한다. T14·T17의 그래프 연결은 T13-2 뒤에 수행한다. T15는 T14 뒤에 수행한다. T16은 T17의 `근거 부족` 상태에서만 T14를 한 번 거쳐 재검색하고, T13-2 뒤 그래프에 연결한다.
- **.arp 생성**: 자유 텍스트 생성 금지. T19에서 실행 요청에 필요한 키를 선택하고 제약을 정의한 뒤 구조화 생성한다. T2의 PPVERSION 기록과 **ART-cli 실행 자체**를 검증 기준으로 사용한다.
- **코퍼스 정책**: GitHub Issues·Discussions는 공개 API·검색 전용(재배포 아님)으로 주 1회 증분 동기화한다. T10-1이 원문 변경분을 보관하고, T10-2a가 실제 플랫폼 신호에 따른 검색 후보 정제 규칙을 만든다. T8-2가 정제된 GitHub 후보를 해당 글 구조에 맞게 청킹해 공통 실험에 제공한다. T10-2c는 선정 뒤 같은 규칙으로 변경분만 T9 저장소에 반영한다. 원문 동기화 상태와 벡터 반영 상태는 별도로 기록한다.

## 후속 계획 · RAG 서비스 적용

최신 `main`에서 서비스 적용 브랜치를 시작한다. PR #25의 `--improved`로 확인한 검색과 인용 개선을 GUI의 Python 브리지와 대화형 CLI에서 선택할 수 있게 한다. 주 대상은 RawPedia와 ART GitHub 근거 답변이다. 변경 범위는 `src/artagent/`의 Python 경로다. GUI의 기존 요청·응답 형식, ART 편집·렌더링 동작, A-23 완료 기준을 보존한다. [평가 결과](../docs/RAG_minimax_search_optimization.md) · [GUI 연결 계약](../docs/T22_execution_plan.md)

### 실행 경로와 설정

1. **기존 경로를 기준선으로 동결한다.** GUI와 CLI가 실제 여는 Chroma 컬렉션, 모델 revision, 활성 청크 지문, 설정된 답변 제공처를 기록한다. 평가의 158청크와 서비스 색인 차이를 먼저 확인한다. 기존 100문항과 F01–F08은 회귀에 사용한다. 새 질문의 원문 ID와 기대 상태는 후보 답변을 보기 전에 고정하고, 두 출처, 한국어 UI 명칭, 명시 이슈 번호, 근거 부족과 미지원 사례를 포함한다.
2. **로컬 검색 개선을 공통 옵션으로 연결한다.** 두 진입점이 하나의 Python 설정을 읽도록 한다. 초기 설정은 기존 경로이며 검증용 설정 예시는 `ART_RAG_PROFILE=local`이다. 첫 검색어는 원질문이고 RawPedia에서만 검증된 한영 UI 용어를 보강한다. GitHub 출처와 이슈·Discussion 범위는 원요청으로 결정한다. 현재 Chroma의 임베딩과 활성 청크를 사용해 BM25를 구성하고 후보 20·최종 5·최소 점수 0.5·가중치 0.75를 서비스 색인에서 다시 검증한다. BM25와 벡터 검색의 청크는 같은 색인 세대를 사용한다. GUI는 작업 요청마다 Python 프로세스를 실행하므로 초기화 지연도 측정하고, 필요할 때만 색인 지문을 기준으로 재사용한다.
3. **근거 답변과 재검색을 검증한다.** 같은 옵션으로 본문 인용 표식의 자동 조립을 켠다. 검색 문맥에 없는 ID와 잘못된 표식 형식은 오류로 처리한다. 근거 부족 재검색은 기존 1회 예산을 사용한다. 재작성 검증에 실패하면 같은 출처·범위에서 원질문을 쓰고, 첫 검색과 질의가 같으면 첫 근거 부족 답변을 돌려준다. GUI의 실제 실행 환경에서 옵션 전달, 근거 표시와 오류 형식을 확인하고 CLI에도 같은 동작을 대조한다.
4. **MiniMax 답변 선택을 별도로 검증한다.** 같은 검색 문맥에서 기존에 설정한 답변 모델과 MiniMax를 비교한다. MiniMax에 대한 설정은 RAG 답변 호출에만 적용하며 공유 환경변수를 요청마다 덮어쓰지 않는다. `429`·`529`·시간 초과 시 명시적으로 설정된 대체 모델이 있으면 남은 요청 예산에서 한 번 호출한다. 대체 모델이 없거나 예산을 소진하면 기존 답변 생성 오류 계약을 사용한다. 호출과 폴백 여부, 지연, 토큰 사용량을 검증 기록에 남긴다.

`현재 서비스 기준선 → 로컬 개선 연결 → GUI·CLI 회귀 → 로컬 기본값 판정` 순서로 진행한다. MiniMax 실호출은 같은 문맥을 확보한 뒤 별도 판정한다. NVIDIA가 응답하는 시점과 관계없이 로컬 개선을 연결하고 검증할 수 있다.

### 기본값 전환과 복구

| 대상 | 전환 판단 | 복구 |
| --- | --- | --- |
| 로컬 검색·인용 | 실제 서비스 기준선과 같은 색인·답변 설정에서 출처별 원문 재현율을 유지하고 반증 원문 5/5를 확보한다. 새 질문에서 기대 상태와 인용을 원문에 대조하고, F01 `Crop` 근거와 F08 인용을 실제 진입점에서 확인한다. 콜드 시작과 검색 p50·p95를 기준선과 비교한다. | 설정을 기존 경로로 돌려 GUI·CLI의 첫 검색과 답변을 재현한다. |
